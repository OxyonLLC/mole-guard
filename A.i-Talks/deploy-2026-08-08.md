## ⚠️ HAZARD — the registration lists (read first)

`src/faucet/airdrops.json` and `src/faucet/registrations.json` are **managed
files**: the faucet writes them at runtime whenever someone runs `!register`,
and mirrors them to Mongo.

Both were cleaned in this repo on 2026-08-07 (153 → 148 payable, removing
the X Faucet Reserve, the Developer Reserve listed twice, 3 duplicates and 4
invalid base58 strings) and the cleaned versions are committed. On 2026-08-08 seven registrations
recovered from the deleted old-PC folder were added back, so the current
committed count is **155** — see
`A.i-Talks/legacy-registrations-recovered-2026-08-08.md`.

**The serving machine has been accepting registrations since 2026-08-06.** Its
copies have almost certainly drifted. Those extra entries are real people, and
`git pull` would overwrite them.

There is a second-order version of the same trap. On boot, `bootstrapFile()`
(`src/faucet/storage.js:106`) resolves local-vs-Mongo like this:

| local | Mongo | winner |
|---|---|---|
| meaningful | meaningful | **local overwrites Mongo** |
| empty | meaningful | Mongo restores local |
| meaningful | empty | local seeds Mongo |

Both sides are meaningful here, so **local wins**. That is what pushes the
cleaned list to Mongo — the desired outcome — but it also means a bad local file
propagates to Mongo on restart and the Mongo copy stops being a fallback.

### Do this on the serving machine, in this order

```bash
cd <serving checkout>

# 1. Snapshot the live lists BEFORE touching git.
mkdir -p ~/faucet-prepull
cp src/faucet/airdrops.json      ~/faucet-prepull/
cp src/faucet/registrations.json ~/faucet-prepull/

# 2. See whether they actually drifted.
git status --short src/faucet/airdrops.json src/faucet/registrations.json
```

**If both come back clean** — no drift, nothing to merge. Skip to *Pull and
restart*.

**If either shows as modified**, find what the serving machine has that the
cleaned list does not.

Both files are a plain **JSON array of base58 address strings** (verified — not
an object keyed by Discord ID, which is what they look like they should be). The
comparison below was run against the real files with a synthetic extra entry to
confirm it actually reports drift rather than silently printing zero:

```bash
git stash push src/faucet/airdrops.json src/faucet/registrations.json
git pull

node -e '
const fs=require("fs");
const flat=o=>{const d=JSON.parse(fs.readFileSync(o,"utf8"));
  const a=Array.isArray(d)?d:(d.entries||d.wallets||Object.values(d).flat());
  return new Set((Array.isArray(a)?a:[]).map(x=>typeof x==="string"?x:(x&&(x.wallet||x.address))).filter(Boolean));};
for (const f of ["airdrops","registrations"]) {
  const live=flat(process.env.HOME+"/faucet-prepull/"+f+".json");
  const clean=flat("src/faucet/"+f+".json");
  const added=[...live].filter(w=>!clean.has(w));
  console.log(f+": live="+live.size+" cleaned="+clean.size+" NEW on server="+added.length);
  added.forEach(w=>console.log("   + "+w));
}'
```

Anything printed with a `+` is a registration made after the clean. Add those
back by hand, then re-run the cleaner to make sure none of them is a reserve
address or duplicate:

```bash
npm run airdrop:clean          # report only — prints, changes nothing
npm run airdrop:clean -- --write
```

Do **not** `git stash pop` the whole file — that reintroduces the reserve
addresses the clean removed.

### yarn was removed 2026-08-08 — what the serving machine must do

`yarn.lock`, `.yarnrc.yml` and the `packageManager` field are gone. **npm is now
the only package manager.**

Two things that sound like they follow from this but do not:

- **`node_modules` does NOT need deleting because of the yarn removal.**
  Removing a lockfile from git does not touch an installed tree. The serving
  machine has been installing with `npm ci` per this runbook, so its
  `node_modules` is already an npm tree and is unaffected.
- **Use `npm ci`, not `npm install`.** `npm install` may *rewrite*
  `package-lock.json` to satisfy ranges, which on a serving machine means the
  deployed tree silently drifts from the committed one. `npm ci` installs
  exactly what the lockfile says and errors if they disagree.

`node_modules` does need refreshing, but for a different reason: the dependency
review changed `package-lock.json` (axios removed, several packages patched).

```bash
git pull
npm ci                      # NOT npm install
npm test                    # expect 951/951, 0 skipped
npm run verify:imports      # every module the bots import resolves
npm run pm2:restart
```

If the machine has a stale `.yarn/` directory or `yarn.lock` left over locally,
delete them — they are now gitignored and cannot come back through a pull.

### ⚠ `npm ci` can fail on a WSL `/mnt/c` checkout

The dependency review changed `package-lock.json`, so `npm ci` is required this
deploy rather than optional.

If the serving checkout lives under `/mnt/c` (WSL's 9p/v9fs mount), `npm ci`
may fail part-way with:

```
npm error ENOTEMPTY: directory not empty, rmdir '.../node_modules/zod/v4/classic'
```

That is a filesystem limitation, not a broken lockfile — v9fs cannot remove a
directory another process still has open, and `npm ci`'s clean step trips on
it. It happened on the laptop on 2026-08-08 and left a partial 32-package
install.

**Workaround — remove first, then install:**

```bash
rm -rf node_modules && npm ci
```

If it still fails, `npm install` (which does not do the aggressive clean) will
produce a tree matching the lockfile. Verify afterwards with:

```bash
npm ls >/dev/null && echo "tree matches lockfile"
npm run verify:imports
npm test
```

A checkout on the Linux filesystem (`~/…`) does not have this problem, and
neither does CI, which runs on ext4.

**Discord command re-registration is NOT needed this time.** The governance
change alters behaviour, not command shape, and no command *description*
contains a threshold — checked. Skip `register:mole` / `register:quiz`.

## What is actually changing, and how to check it

### 1. Governance split gate

The free vote is back. Any verified wallet with a non-zero balance gets exactly
one vote — that is the whole of one-wallet-one-vote. **1,000,000 WinLEW** is now
only the bar for *buying extra weight*, not for voting at all.

`resolveVoteWeightInfo()` fails closed: if the balance cannot be read, extra
weight is refused rather than granted. All four call sites pass the balance (3
routes + `commands.js:431`).

Check: a verified holder with a small balance can vote and sees no purchase
option; `/mole proposals` still renders.

### 2. The 25M faucet lock on `/transparency/`

New component `lock25mFaucet` → `8jr1Zov74VbbDyvuW55Hei2LgMuki9N5W2hUVnB2f986`
(Jupiter Lock, 10-year, funded from the X Faucet account). The tokenomics
paragraph was updated to match — a test now fails if a lock component exists
that the prose does not mention, which is the exact drift that once
under-reported locked supply by 7M.

Check: `/transparency/` lists the 25M lock and the paragraph totals include it.

### 3. Raydium pool now shows its real position

Two new components, `liquidityVaultWinlew` and `liquidityVaultSol`, read the
pool's actual vault token accounts. The existing "Established Raydium Pool"
component points at the PoolState account, which holds only rent — so the page
was showing ~0.0053 SOL for a pool containing **35,491,700.64 WinLEW** and 4.78
wrapped SOL.

Check after restart: `/transparency/` shows a WinLEW-side figure in the 35.4M
range and a SOL side near 4.78. Both come from the API, so no static upload is
involved beyond the page already listed above.

**Do not let anyone re-label these as locked supply.** The pool is bigger than
any single lock on the page, so the temptation is real, but LP holders can
withdraw it at any time with no cliff — and 53.66% of the LP is held by the
Developer Reserve. Two tests enforce the wording; if one fails, the wording was
right and the edit was wrong.

### 4. Live price widgets — all of them were broken

The landing page's "How to Buy" card showed "—" for PRICE, MARKET CAP, 24H
VOLUME, LIQUIDITY, BURN PROGRESS and CIRCULATING SUPPLY. `/home/` said
"Couldn't load verified market data right now." One cause for all of it: those
pages called `/api/...` directly, and **Apache 404s every `/api/*` path on
winlew.co** — only `/verify/api-proxy.php` reaches Node. Verified live.

The price sources were never at fault; GeckoTerminal answers for all three
markets right now.

This is a **static-upload-only** fix — no backend change. After uploading,
check the landing card shows real numbers and `/home/`'s Primary/Raydium tabs
populate. `/winlew-forge/`'s AI step had the identical bug and is also fixed.

Also fixed in the bot (needs the restart, not the upload): `!data`'s Raydium
row, which had never worked, and thousands separators on every balance and
supply the bot prints.
